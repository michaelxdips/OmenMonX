## 0. Corrections to the previous handoff (important)

The v3 handoff contained two premises that are **false**. They are corrected here so no
further work is built on them.

### 0.1 REFUTED - "SSD3.aml 0x0A600 is a command list for hpCpsPubGetCommand"

The bytes at `SSD3.aml` offset `0x0A600` are:

```
0A600: 08 42 45 52 50 12 48 06 18 0D 4E 61 6D 65 00 0D  .BERP.H...Name..
0A610: 56 61 6C 75 65 00 0D 53 79 73 74 65 6D 20 43 6F  Value..System Co
0A620: 6E 66 69 67 75 72 61 74 69 6F 6E 00 00 01 00 00  nfiguration.....
0A630: 01 0D 20 00 00 0D 45 6E 61 62 6C 65 00 0A 0C 0D  .. ...Enable....
0A640: 45 6E 61 62 6C 65 00 0D 44 69 73 61 62 6C 65 00  Enable..Disable.
```

This is `Name(BERP, Package{ "Name", "Value", "System Configuration", 0, 1, 0, 0, 1,
" ", 0, "Enable", 0x0C, "Enable", "Disable", ... })` - a **WMI property descriptor
template**, not a command list. There are no `GetXxx`/`SetXxx` strings in this region.

### 0.2 REFUTED - "EC 0xC6/0xC7/0xC8 are live CPU power"

Those registers are static limits. The actual live-power question is settled in §3.

### 0.3 REFUTED - "hpCpsPubGetCommand needs a full instance path, class-level fails"

Class-level `Invoke-CimMethod` fails, but so does everything else **until the signature
is right**. The real blocker was `SignIn`, not the invocation path. See §2.

## 1. The hpCps command channel - signature gate CRACKED

**VERIFIED.** The channel is fully open.

### 1.1 Where it lives

| Item | Value |
|---|---|
| Namespace | `root\wmi` |
| Class | `hpCpsPubGetSetCommand` |
| Instance | `ACPI\PNP0C14\H19P_0` |
| GUID (class qualifier) | `{928b5a30-ad7c-4c36-946a-1300a80ce7e1}` |
| ACPI table | `SSD1.aml` (2282 bytes), OEM id `HPQOEM8C9C` |
| ACPI device | `\_SB.CPWM`, `_HID = PNP0C14`, `_UID = "H19P"` |

### 1.2 Methods

```
hpCpsPubGetCommand(Command: String, SignIn: UInt32)
    -> ReturnCode: UInt32, DataSizeOut: UInt32, hpqBDataOut: UInt8Array
hpCpsPubSetCommand(Command: String, DataSizeIn: UInt32,
                   hpqBDataIn: UInt8Array, SignIn: UInt32)
    -> ReturnCode: UInt32
```

### 1.3 The signature gate

`SSD1.aml` contains:

```
0x054C: "BUFR"   data buffer object
0x0555: "SGNT"   signature object
0x055D: "HCPW"   literal
0x0564: "CKSG"   check-signature method
0x060D: "CKCD"   check-command method
```

`SGNT` is `Buffer(4){"HCPW"}` and `CKSG()` compares the caller's `SignIn` against it
byte-by-byte. Therefore:

```
SignIn = 0x57504348    // "HCPW" read as a little-endian u32
```

### 1.4 Return codes (measured)

| rc | Meaning | How proven |
|---|---|---|
| **0** | command accepted | `SampleGetCmd` with correct SignIn |
| **2** | **signature rejected** (CKSG failed) | any command with `SignIn=0` |
| **3** | signature OK, **command unknown** (CKCD failed) | `GetThermalMode` with correct SignIn |

Live proof:

```
GET cmd='SampleGetCmd' signIn=0x57504348 -> rc=0 size=4 data=[08 00 00 00]
GET cmd='GetThermalMode' signIn=0x57504348 -> rc=3 size=0 data=[]
SET cmd='IntelACA'       signIn=0x57504348 -> rc=0 ret=True
SET cmd='SampleGetCmd'   signIn=0x57504348 -> rc=3 ret=True
```

### 1.4b The WQBB blob is ENCRYPTED, not compressed - proven by exhaustion

SSD1.aml also contains Name(WQBB, Buffer(1151)) at x00B1. Its payload starts with
"FOMB" (BMOF magic, i.e. a Binary MOF / WMI schema image), version 1, declared
compressed size 1151, declared uncompressed size 4684 (ratio 4.07 - the classic
LZNT1 ratio, which is why it looks decodable).

**It is not decodable.** Measured properties of the 1151-byte body:

| property | value | what it rules out |
|---|---|---|
| distinct byte values | **238 / 256** | any structured/table format |
| zero bytes | **18 (1.6 %)** | BMOF, which is NUL-heavy |
| UTF-16 runs >= 4 chars | **0** | BMOF (must contain class/method/property names) |
| ASCII runs >= 5 | 3 accidental (]X<)x, Z}*5fl, J{'h() | any readable schema |
| compression magic (78 9C, 78 01, 78 DA, 1F 8B, PK) | **none anywhere** | zlib/gzip/zip |

Decoders attempted, all negative:

1. **LZNT1** — full implementation, swept at every start offset 0-8. Every run produced
   ~1146 bytes with zero UTF-16 runs. (Chunk headers do not validate.)
2. **Byte-plane de-interleave** — 4 permutations (halves-interleave, halves-reverse,
   even/odd split both ways). Zero UTF-16 runs.
3. **Repeating-XOR key search** — all 256 single-byte keys, scored by the UTF-16
   zero-byte lattice. Best score 12/576, no key produces a lattice.
4. **Deflate/zlib/gzip/zip magic scan** — zero hits in 1151 bytes.

**Conclusion: the blob is encrypted with a scheme not present in this table.** It is
also **not needed**: the AML gives us the complete wire format directly (§1.3, and the
CKCD/SIAS decode in §1.4), and the only two command strings it could possibly
describe are the two we already have. Do not spend further effort on it.
### 1.4c _WDG decoded - the class is firmware-registered, which is why no DLL has the name

SSD1.aml _WDG at x0075, three 20-byte entries. GUIDs decoded per Windows
layout (Data1/Data2/Data3 little-endian, Data4 as-is):

| # | GUID | ObjectId | Inst | Flags |
|---|---|---|---|---|
| 1 | 928b5a30-ad7c-4c36-946a-1300a80ce7e1 | x4242 ("BB") | 1 | x02 METHOD |
| 2 | 8a5318a3-7393-4d54-979c-89483522e383 | x00D1 | 1 | x08 EVENT |
| 3 | 5901221-d566-11d1-b2f0-00a0c9062910 | x4242 ("BB") | 1 | x00 RESOURCE |

Entry 1 matches the live class qualifier **exactly**:

`
Get-CimClass root\wmi hpCpsPubGetSetCommand -> guid {928b5a30-ad7c-4c36-946a-1300a80ce7e1}
`

x4242 is ASCII "BB" — WM+BB = WMBB (the method), WQ+BB = WQBB (the BMOF
buffer). Entry 2's x00D1 is the constant _WED compares Arg0 against, which
independently proves the ObjectId sits at +16 and Instance is 1 byte at +18.

**This explains the negative binary scan.** The WMI class name is generated by
WmiProv from this _WDG table at runtime; no DLL ever contains the literal string
hpCpsPubGetCommand. A ~19,000-file scan across DriverStore, System32, the whole OGH
tree, Program Files\HP, ProgramData and both HP capability packages returned **zero**
hits for hpCps* — which is correct and expected, not a gap in the search.

### 1.4d Two corrections to a subagent's report

A parallel investigation reported two things that are wrong. Verified directly:

1. **"WMIService.dll does not contain hpqBIntM"** — **false.** It does, as UTF-16:
   hpqBIntM, hpqBDataIn, CommandType, hpqBIOSInt all present. The original note
   was correct. (SystemPropertiesService.dll also contains them; both files carry the
   legacy hpqBIntM path.)
2. **"WMBB returns fixed payloads 2/3 for the two commands"** — **imprecise.**
   x02 and x03 are the *failure* status codes (bad signature / unknown command).
   SampleGetCmd returns 8 00 00 00 on success, measured live.

Also confirmed rather than assumed: WMBB's 326-byte body references **Arg1 exactly
twice** and **Arg0 zero times**, so there are exactly two dispatch branches and no
third command path. The other four IfOps in the body are nested inside those two.
### 1.5 REFUTED - this channel does anything useful on this board

The AML implements only **two** command strings, both of which are Insyde's own
sample/test placeholders, not HP features:

| Offset | Method | Buffer contents |
|---|---|---|
| `0x06B3` | `SC01` (set) | `Buffer(0x12){"IntelACA"}` |
| `0x0749` | `GC01` (get) | `Buffer(0x1A){"SampleGetCmd"}` |

`IntelACA` returns **rc=3** on GET (it is set-only). `SampleGetCmd` returns a constant
`08 00 00 00` regardless of input. There is no dispatch table mapping feature names to
EC/SMU operations - `WMBB` takes `(MBGS, 0x57, index)` and branches only on
`Arg1 == 1` (set) / `Arg1 == 2` (get).

**Conclusion:** the channel is a real, working, signed Insyde plumbing layer with **no
HP feature vocabulary behind it on this board**. Nothing to harvest. Do not spend more
time here.

## 2. The InstrumentedBIOS channel - writes DO work

**VERIFIED.** This corrects the earlier "read-only" conclusion.

### 2.1 The critical detail

`SetBIOSSetting` **must be invoked on the instance object**, not the class:

```powershell
$inst = Get-CimInstance -Namespace ROOT\HP\InstrumentedBIOS `
                        -ClassName HPBIOS_BIOSSettingInterface
Invoke-CimMethod -InputObject $inst -MethodName SetBIOSSetting `
                 -Arguments @{ Name='Fan Always On'; Password=''; Value='Enable' }
```

Class-level `Invoke-CimMethod ... -ClassName` returns rc=5 for everything and looks
like a permissions failure. It is not - it is the wrong invocation shape.

Signature:

```
SetBIOSSetting(Name: String, Password: String, Value: String) -> Return: UInt32
SetSystemDefaults(Password: String, SetPolicyDefaults: Boolean) -> Return: UInt32
```

Instance: `ACPI\PNP0C14\0_0`, `Active = True`.

### 2.2 Return-code semantics - calibrated, not guessed

Calibrated by writing a known-good setting with known-good and known-bad values:

| rc | Meaning | Evidence |
|---|---|---|
| **0** | accepted | `Fan Always On` ← `Enable` / `Disable` |
| **1** | **name does not exist** | `ZZZZ_Not_A_Setting` ← anything |
| **5** | **name exists, value rejected** | `Fan Always On` ← `BogusValue123` |
| **6** | accepted, needs reboot | `Battery Remaining Time` ← `Disable` |

Round-trip proof:

```
Fan Always On current = 'Disable'
  write 'Enable'  -> Return=0
  after           = 'Enable'    CHANGED=True
  write 'Disable' -> Return=0
  RESTORED        = 'Disable'   ok=True
```

### 2.3 Full enumerated setting list (23 entries, all read via HPBIOS_BIOSEnumeration)

Writable (`IsReadOnly = false`) settings observed: `Adaptive Battery Extender`,
`Adaptive Battery Extender Status`, `Fan Always On`, `Network Boot`, `Action Key Mode`,
`USB Boot`, `POST Hotkey Delay (sec)`, `Battery Remaining Time`, `Legacy Support`,
`TPM Device`, `TPM State`, `OOBE`, `PIN Load Defaults`, `Clear Event Log`, `Language`,
`Network Boot Protocol`, plus a `Feature Byte` string setting.

### 2.4 Hidden-but-writable settings discovered

`Legacy Support` is **not enumerated** (returns empty `CurrentValue`) yet accepts
writes with **rc=0** for both `Enable` and `Disable`. This proves the BIOS holds a
settings namespace larger than the one it exposes through `HPBIOS_BIOSEnumeration`.

**This is the most promising remaining lead for the battery question.** See §5.

## 3. CPU power - what is and is not controllable

### 3.1 REFUTED - "0x2A is live CPU package power"

Measured idle vs 16-thread load:

```
idle            samples=6  min=64 max=65 avg=64   raw=[65,64,64,64,65,65]
load            samples=8  min=61 max=64 avg=62   raw=[64,64,62,62,62,62,61,61]
idle-after-load samples=5  min=62 max=62 avg=62   raw=[62,62,62,62,62]
```

Load power is **lower** than idle. `0x2A` is not instantaneous power.

### 3.2 VERIFIED - 0x2A is a configured-limits block

Ten samples at idle, per byte:

```
[0] varies   min=60 max=62   <- this byte is what fluctuates
[1] STABLE   = 0
[2] STABLE   = 25      <- PL1
[3] STABLE   = 25      <- PL2
[4] STABLE   = 25      <- PL4
[5] STABLE   = 0
[6] STABLE   = 0
[7] STABLE   = 35      <- PL with GPU
[8..11] STABLE = 0
```

Full block at idle: `3E 00 19 19 19 00 00 23 00 00` → PL1=PL2=PL4=**25 W**, PLwGpu=**35 W**.

**INFERRED:** byte 0 (60–62) is likely a thermal or utilisation scalar, not watts -
it never exceeds 65 and does not track load.

### 3.3 VERIFIED - `0x29` DOES work, but only in a narrow window

This is the single most important correction in this report. My first two tests of
`0x29` used the wrong byte order and concluded "silent no-op". **That was wrong.**
Recovering the byte order from OMEN Gaming Hub's IL (§7.7) and retesting produced a
reliable, repeatable write.

#### The two payload forms

**Form B - concurrent TDP** (`PerformanceControlHelper.SetConcurrentTdpLegacyV2`):

```
payload = { 0xFF, 0xFF, 0xFF, tdp }      // byte 3 is the value
```

Writes `0x2A[7]`. Confirmed 7/7 with an ascending-then-descending sweep:

| wrote | `0x2A[7]` after | match |
|---|---|---|
| 20 | 20 | YES |
| 26 | 26 | YES |
| 32 | 32 | YES |
| 38 | 38 | YES |
| 32 | 32 | YES |
| 26 | 26 | YES |
| 20 | 20 | YES |

Restored to the original value, verified. **This is the `WithGpu` / concurrent-TDP
field.**

**Form A - PL1/PL2** (`PowerControlBase.SetPowerLimit`):

```
payload = { pl2, pl1, 0xFF, 0xFF }      // PL2 FIRST, then PL1
```

Writes `0x2A[2]`, `0x2A[3]`, `0x2A[4]`. Sweep with `pl1 == pl2`:

| wrote | `[2]` | `[3]` | `[4]` | result |
|---|---|---|---|---|
| 5 | 5 | 5 | 5 | **ACCEPTED** |
| 10 | 10 | 10 | 10 | **ACCEPTED** |
| 15 | 15 | 15 | 15 | **ACCEPTED** |
| 18 | 18 | 18 | 18 | **ACCEPTED** |
| 20 | 20 | 20 | 20 | **ACCEPTED** |
| 22 | 22 | 22 | 22 | **ACCEPTED** |
| 24 | 24 | 24 | 24 | **ACCEPTED** |
| 25 | 25 | 25 | 25 | **ACCEPTED** |
| 26 | 25 | 25 | 25 | rejected → reset |
| 28 | 25 | 25 | 25 | rejected → reset |
| 30 | 25 | 25 | 25 | rejected → reset |
| 35 | 25 | 25 | 25 | rejected → reset |
| 40 | 25 | 25 | 25 | rejected → reset |

**Clean, unambiguous clamp: 5–25 W accepted, ≥26 W rejected and the firmware resets
the field to 25.** Restored and verified.

#### What this means

- There **is** a working CPU power envelope on this board: **5 W to 25 W**.
- The 25 W ceiling is a hard platform limit, consistent with `0x2A` defaulting to
  `19 19 19` (25/25/25) and `SystemData.DefaultCpuPLwGpu = 0x23` (35 W).
- `0x28[6] = 0x00` (`BiosOc = NotSupported`) does **not** block this - `0x29` is a
  different, permitted path.
- This is a **power cap**, not a boost unlock. It cannot raise performance above the
  platform default; it can only lower it (useful for thermal/noise/battery).

#### 3.3b The cap has a REAL EFFECT on the machine - proven by outcome

Writing a register is not the same as changing behaviour. That is exactly the mistake
that made `MP1 0x14` look functional. So the cap was verified by **outcome**, with the
same rigour used to disprove `MP1 0x14`.

Method: sustained 16-thread load, live clock from
`\Processor Information(_Total)\Actual Frequency` (a genuine counter - it reads
3967 MHz at idle, not the nominal 3801). Alternating 25 W / 10 W / 25 W / 10 W / 25 W
so thermal drift cancels across phases.

| phase | wrote | register readback | clock mean | min | max |
|---|---|---|---|---|---|
| 1 | **25 W** | [25,25,25] | **3393 MHz** | 3378 | 3417 |
| 2 | 10 W | [10,10,10] | 3058 MHz | 1605 | 3476 |
| 3 | **25 W** | [25,25,25] | **3386 MHz** | 3376 | 3400 |
| 4 | 10 W | [10,10,10] | 1840 MHz | 1400 | 3358 |
| 5 | **25 W** | [25,25,25] | **3381 MHz** | 3332 | 3437 |

- **25 W is rock-steady: 3393 / 3386 / 3381 MHz - a 12 MHz spread across three separate
  phases separated by load excursions.** That reproducibility is the proof the
  measurement is sound.
- **10 W collapses: 3058 and 1840 MHz.** The variance is high because a 10 W budget
  cannot hold 16 threads boosted; cores fall to idle clocks between work quanta.
- **The ranges do not overlap by 1541 MHz** (lowest 25 W = 3381 vs highest 10 W = 1840).

**Verdict: `0x29` form A is a genuine, working power cap.** It changes how the machine
runs, not just what a register reads. Restored to baseline and verified.

Contrast with `MP1 0x14` (§4.7), where the same style of test produced
3293 / 3291 / 3349 MHz - no separation, inconsistent sign, i.e. noise. The difference
between the two results is the whole point: one control works and one does not.

#### Why the first tests failed

| test | payload | why it failed |
|---|---|---|
| 1st | `{PL1, PL2, PL4, 0}` as 4 bytes | wrong byte order |
| 2nd | 4 × `u32` (16 bytes) | wrong width entirely |
| 3rd | `{45, 45, 190, 0}` | 45 W is above the 25 W clamp → rejected, reset to 25, looked like a no-op |

Only the combination of **correct byte order** *and* **a value inside 5–25 W** produces
an observable change.

## 4. AMD SMU access - full mailbox control achieved

This is the deepest layer reached, and it works.

### 4.1 The transport

`OmenCore` (github.com/theantipopau/omencore) ships a **namazso-signed PawnIO module**,
`RyzenSMU.bin` (38 996 bytes), at
`src/OmenCoreApp/drivers/RyzenSMU.bin`. It is already trusted by the PawnIO driver
installed on this machine (`C:\Windows\System32\drivers\PawnIO.sys`, service `PawnIO`,
state Running).

Its exported entry points (read from the module's string table at `0x002CA`–`0x003F2`):

```
ioctl_get_code_name        ioctl_get_smu_version
ioctl_read_pm_table        ioctl_read_smu_register
ioctl_resolve_pm_table     ioctl_send_smu_command
ioctl_update_pm_table      ioctl_write_smu_register
unload                     cpuid
pci_config_write_dword     pci_config_read_dword
io_space_unmap             io_space_map
debug_print                virtual_read_qword
get_arch
```

### 4.2 Live results on this machine - VERIFIED

```
module: 38996 bytes, loaded OK
ioctl_get_smu_version   -> 0x004C5D00
ioctl_resolve_pm_table  -> version 0x004C0009, base 0x7E300000
ioctl_read_pm_table     -> 4096 bytes, 1015 non-zero
ioctl_read_smu_register(0x3B10528) -> 0x00000011
ioctl_read_smu_register(0x3B10578) -> 0x00000001
```

### 4.3 Mailbox addresses for this CPU

Hawk Point (family 0x19, model 0x75) per OmenCore's `ConfigureSmuAddresses`:

| Mailbox | msg | rsp | arg |
|---|---|---|---|
| MP1 | `0x3B10528` | `0x3B10578` | `0x3B10998` |
| PSMU | `0x3B10A20` | `0x3B10A80` | `0x3B10A88` |

### 4.4 Mailbox protocol (implemented and working)

From `RyzenSmu.SendMsg`, reproduced in Rust and confirmed working:

1. Poll `rsp` until non-zero (SMU idle).
2. Write `rsp = 0`.
3. Write six u32 args to `arg + 4*i`.
4. Write `msg = <message id>` - this starts execution.
5. Poll `rsp` until non-zero; the value is the status.
6. Read args back.

Measured status `0x1` (OK) for `MP1 0x02` (GetSmuVersion) and `MP1 0x14` (SetStapm).

### 4.5 SMU message IDs recovered from OmenCore (RyzenAdj-verified upstream)

| ID | Mailbox | Operation |
|---|---|---|
| `0x02` | MP1 | GetSmuVersion |
| `0x14` | MP1 | set_stapm_limit (fallback PSMU `0x31`) |
| `0x15` | MP1 | set_fast_limit |
| `0x16` | MP1 | set_slow_limit |
| `0x23` | MP1 | set_apu_slow_limit |
| `0x4C` | MP1 | set_coall (all-core Curve Optimizer) |
| `0x4B` | MP1 | set_coper (per-core CO) |
| `0xB7` | PSMU | set_cogfx (iGPU curve) |
| `0x5D` | PSMU | CO alternate path |
| `0x55` | MP1 | CO alternate (G-Helper formula `0x100000 - |offset|`) |

CO value encoding for negative offsets: `0x100000 - (uint)(-offset)`.

### 4.6 REFUTED - the PM table is live telemetry

Sampled 12 times at idle, then 12 times under 16-thread load:

```
idle: total fields that moved: 0
load: total fields that moved: 0
fields whose MEAN differs strongly between idle and load: (none)
```

`ioctl_update_pm_table` returns **`0x8007054F` (internal error)** - it cannot refresh.
Two consecutive raw reads differ in **0** fields.

**Conclusion:** on this board the PM table is a **static snapshot written once at
boot**, not a live metrics buffer. It cannot be used for real-time power, temperature,
or per-core clock telemetry. This is why `0x4C0009` has no layout in OmenCore -
there is nothing live to anchor against.

### 4.7 VERIFIED - `MP1 0x14` (SetStapm) has no measurable effect

Run with an independent oracle (`typeperf \Processor Information(_Total)\Actual
Frequency`, a genuine live counter - confirmed varying 3853→3991 MHz at idle):

```
Phase 1  STAPM = 25 W   mean = 3293.2 MHz
Phase 2  STAPM = 45 W   mean = 3290.8 MHz
Phase 3  STAPM = 25 W   mean = 3349.2 MHz   <- highest, and it is the 25 W phase
```

Both writes returned status `0x1` (accepted). But 45 W measured **lower** than the
first 25 W phase, and the second 25 W phase measured **highest of all three**. The
signs are inconsistent and the third phase - which should match the first - is 56 MHz
apart from it.

**Conclusion: this board accepts `MP1 0x14` and ignores it.** Combined with §4.6 (the
PM table is a static snapshot that cannot be refreshed), there is no readback and no
effect. The CPU power limit is fixed by the platform.

> Methodology note: an earlier run of this test used
> `\Processor Frequency`, which returned a constant 3801 MHz in all three phases. That
> counter is the nominal/rated clock, not a live measurement - the test was
> **inconclusive, not negative**, and was rerun with the correct counter.

## 5. Battery charge limit - the answer

The user asked specifically whether a charge limiter is possible on this board.
Here is the complete evidence chain.

### 5.1 Every channel tested

| Channel | Test | Result |
|---|---|---|
| BIOS setting `Battery Care Function` | `SetBIOSSetting` with 27 value encodings | **rc=5 always** - name exists, every value rejected |
| BIOS setting `Battery Health Manager` | same | **rc=5 always** |
| 10 other HP battery-care names | same | **rc=1** - names do not exist |
| BIOS enumeration | full `HPBIOS_BIOSEnumeration` dump | no charge-limit setting present |
| BIOS password gate | 9 passwords including empty | rc=5 regardless - not a password issue |
| `Setup Password IsSet` | `HPBIOS_BIOSPassword` | **0** - no password set |
| ACPI `_BTP` | disassembled | present, writes `EC0_BTPP` |
| `ECMM` region | parsed field list | `BTPP` at byte 1350, bit 7, 16 bits → absolute `0xFC7E0546` |
| ECMM access | PawnIO `LpcACPIEC` (ports 0x62/0x66 only) | **cannot reach MMIO** |
| EC direct registers | full 256-byte page dump | no charge-limit register |
| OmenCore | full source search for charge-limit | **zero implementations** |
| OMEN Gaming Hub | string scan of 3 550 files | no charge-control API |
| hpCps channel | cracked, then enumerated | no battery command exists |

### 5.2 The `_BTP` finding - real, but unreachable through this path

`DSDT.aml` at `0xAF86` contains:

```asl
Method (_BTP, 1) {
    Local0 = Arg0 / BASC      // BASC = 1 (battery count)
    Store (Local0, EC0_BTPP)  // EC0_BTPP lives in ECMM
    Return (Local0)
}
```

`_BTP` is the **ACPI Battery Trip Point** - the standard method an OS uses to set a
charge threshold. It exists and it works. But it writes to `EC0_BTPP`, which is a field
of:

```
OperationRegion (ECMM, SystemMemory, 0xFC7E0000, 0x1000)
```

That is **memory-mapped I/O**, not the classic `0x62/0x66` EC port pair. The PawnIO
`LpcACPIEC` module on this machine whitelists only ports `0x62` and `0x66`, so it
cannot read or write `0xFC7E0546`.

```
ioctl_read_mmio        -> ERR 0x80070002 (entry point absent)
read_mmio              -> ERR 0x80070057
ioctl_read_physical    -> ERR 0x80070002
```

### 5.3 Why `Battery Care Function` returns rc=5

`rc=5` means *the BIOS knows this setting name but rejects this value*. This is
consistent with the setting existing in the Insyde setup-variable namespace but being
**gated behind a platform capability flag that is off on this board**, or expecting a
value encoding that the WMI layer will not accept from outside the setup UI.

**INFERRED:** HP ships one BIOS image across several SKUs. `Battery Care Function` is
present in the image but the Victus 16 (8C9C) SKU does not enable it. This matches the
fact that HP's consumer Victus line does not advertise battery care in its spec sheet,
while HP's business EliteBook line does.

### 5.4 Verdict

**A battery charge limit is NOT achievable on this board through any software-reachable
channel.** Not through BIOS settings, not through the EC port pair, not through hpCps,
not through the SMU, not through OMEN Gaming Hub, and not through OmenCore (which has
never implemented one).

The only theoretical path is `_BTP` → `ECMM` MMIO at `0xFC7E0546`, which requires a
PawnIO module that exposes physical-memory access. The existing `Hpecmp.bin` in this
repo is a **placeholder**, not a module:

```
EF BB BF "PLACEHOLDER - replace with namazso-signed Hpecmp.bin from PawnIO.Modules PR"
```

**If you want to pursue it**, the concrete next step is: write a PawnIO module that
exposes `ioctl_read_physical` / `ioctl_write_physical` over the `0xFC7E0000` window,
get it signed by namazso, then call `_BTP(80)` through the ACPI method or write
`EC0_BTPP` directly. **This is a real, bounded engineering task - but it is not
guaranteed to work**, because the EC may ignore `BTPP` if the platform flag is off,
which is exactly what `Battery Care Function` returning rc=5 suggests.

**Honest assessment: the probability of success is low, and the downside risk is
real** - `ECMM` is a live firmware mailbox. Writing the wrong offset in a 4 KB
SystemMemory window on an Insyde EC can hang the EC or brick the board. This should not
be attempted without a hardware programmer as a recovery path.

## 6. What genuinely works - the build list

These are the features verified working on this exact machine. Each is a candidate for
the Rust implementation.

### 6.1 Fan table read - VERIFIED, columns decided by evidence

`0x2F` returns 128 bytes: `[0]=fanCount=2`, `[1]=levelCount=42`, then 42 rows with
**stride = fanCount + 1 = 3**.

Two interpretations were tested. OMEN Gaming Hub's `SwFanControlTable` parses with
`stride = NumOfFans + 1` and treats **tuple[0] as a dB level** (`MinDb = 33`,
`GetFanRpm(42)`), i.e. `(dB, fan1%, fan2%)`. My first decode assumed
`(fan1%, fan2%, tempC)`.

Evidence:

| observation | favours dB | favours temperature |
|---|---|---|
| column 2 plateaus at 51/52 for the last 10 rows | consistent with a dB ceiling | implausible: the curve would stop responding above 51 C |
| OGH IL compares tuple[0] against a dB argument | **direct** | contradicts |
| live `0x2D` = 23, 26 | both appear in **column 0** | 26 also appears in column 2 (coincidence) |

All three columns are monotonic, so the table is usable either way.

**Decision: label column 0 `level` (dB) and columns 1..n `fan %`. Do not claim
column 0 is a temperature.** The percentages are unambiguous; the physical meaning of
column 0 is not proven.

```
lvl  Fan1%  Fan2%  TempC
  0      0      0     15
  1     18     21     25
 ...
 20     37     40     41
 ...
 41     58     61     52
```

Range: 15–52 °C maps to 0–61 % duty. This is a real, readable, 42-point fan curve.

### 6.2 Thermal mode write - VERIFIED

`0x1A` with payload `[0xFF, mode, 0, 0]`. `0x28[8]` is the readable status byte:

| mode code | name | `0x28[8]` |
|---|---|---|
| `0x30` | Default / L2 | `0x1E` |
| `0x31` | Performance / L7 | `0x23` |
| `0x50` | Cool / L4 | `0x1E` |
| `0x10` `0x11` `0x20` `0x21` `0x40` `0x04` `0x00` `0x01` `0x02` `0x03` | L0/L5/L1/L6/L3/L8/legacy | `0x1E` or `0x23` |

`0x28[8]` tracks **bit 0** of the mode code exactly. `0x2D` fan levels respond
monotonically to the mode (`0x1C 0x1F` → `0x16 0x19` across the sweep).

### 6.2b Manual fan write (0x2E) - NOT usable on this board

`0x2E` (`SetSwFanControlLevel`) accepts a 128-byte payload with `[0]`/`[1]` as fan
levels. Writes were accepted but **`0x2D` did not track them**:

| wrote | 0x2D after | tracked |
|---|---|---|
| 27 | 23 / 26 | no |
| 37 | 25 / 29 | no |
| 47 | 30 / 33 | no |
| 27 | 31 / 34 | no |
| 32 (4-byte form) | 31 / 33 | no |
| 42 (4-byte form) | 35 / 34 | no |

`0x2D` rose with the writes but kept climbing on its own afterwards, then settled back
to `1C 1F` once the machine cooled. That is **automatic temperature response**, not
the write.

**Safety confirmation after the test:** `EC[0x62] = 0` (manual fan control off),
`EC[0x63] = 0` (no countdown), `EC[0xEC] = 0x63` (max-fan off), fans at
**61 / 49 RPM**, temps 40 C / 49 C, thermal mode back to Balanced.
**Manual fan control never engaged.** The writes were inert.

Conclusion: `0x2E` is a no-op on this board, exactly like `0x32`. Fans are
firmware-managed. Do not build a manual fan slider.
### 6.3 Fan level read - VERIFIED

`0x2D` returns per-fan duty bytes. `0x2C` returns fan types (`0x21` = CPU+GPU nibbles).
`0x10` returns fan count = 2.

### 6.4 Keyboard RGB - VERIFIED, and the zone count is settled

Group `0x20009` command map (all six confirmed live, and matching OMEN Gaming Hub's
own `OmenHsaClient` IL byte-for-byte):

| cmd | function | data size |
|---|---|---|
| `0x01` | HasBacklight | 4 B → `00 43 00 00` |
| `0x02` | GetColorTable | 128 B |
| `0x03` | SetColorTable | 128 B |
| `0x04` | GetBrightness | 4 B → `E4 00 00 00` |
| `0x05` | SetBrightness | 4 B, level in `[0]` |
| `0x06` | GetAnimTable | 128 B → **all zero on this board** |
| `0x07` | SetAnimTable | - |

Live colour table:

```
0x00: 03 00 00 00 ...              <- [0] = zoneCount = 3
0x10: 00 00 00 00 00 00 00 00 00 FF FF FF 07 07 07 00
0x20: 00 FF 07 07 FF 00 00 00 ...
```

Zones at `0x1A + 3*i` as **R, G, B** (this is OGH's `COLOR_OFFSET = 25`, `COLOR_R/G/B
= 0/1/2`, confirmed from IL - **not BGR**):

| zone | R | G | B | populated |
|---|---|---|---|---|
| 0 | 255 | 255 | 7 | yes |
| 1 | 7 | 7 | 0 | yes |
| 2 | 0 | 255 | 7 | yes |
| 3 | 7 | 255 | 0 | **yes - a 4th slot has data** |
| 4–7 | 0 | 0 | 0 | no |

**The `0x2B` discrepancy, resolved by measurement.** OGH's `NbKeyboardLightingType`
says `0x04 = OneZoneWithNumpad` and collapses `ZONE_NUM` to 1 for types 4/5. OmenMon's
enum says `3 = PerKeyRgb`. Our board returns `0x04`, yet `GetColorTable` reports
**`zoneCount = 3`** and three zones carry distinct colours.

**Conclusion: on this board `0x2B = 0x04` means a 3-zone RGB keyboard, and OGH's
enum does not apply.** Drive the zone count from `colorTable[0]`, never from `0x2B`.
`0x2B` is informational only.

`Legacy 0x10` → BornDate **20231222**. `Legacy 0x0F` → AdapterStatus **1** (adequate
power). `0x2B` → KbdType **0x04**.

### 7.7 Performance/thermal/fan subsystem - the authoritative constants

A second full ECMA-335 + IL disassembly pass over the performance modules (plus
`PerformanceControl.dll`, the `Hp.Bridge.Client.SDKs.PerformanceControl` SDK, which is
where all the enums actually live) produced the exact wire semantics.

#### The mode remap - this is why raw mode values do not work

`PerformanceControlHelper.SetFanMode` remaps before sending when
`GetThermalPolicyVersion() == 1` (our board reports V1):

```csharp
switch (mode) {
    case 0: mode = 48; break;   // Default     -> L2 (0x30)
    case 1: mode = 49; break;   // Performance -> L7 (0x31)
    case 2: mode = 80; break;   // Cool        -> L4 (0x50)
}
if (mode == 256) mode = 48;     // Eco -> L2 (0x30)
```

Payload is 4 bytes `{ 0xFF, mode, fanControlByBios, 0 }` to group `0x20008` cmd `0x1A`.
This explains our measured `0x28[8]` behaviour: `0x30/0x50` → `0x1E`, `0x31` → `0x23`.

`PerformanceMode` enum (from the Constant table): `Default=0, Performance=1, Cool=2,
Quiet=3, Extreme=4, L0=16, L1=32, L2=48, L3=64, L4=80, L5=17, L6=33, L7=49, L8=4,
Eco=256`.

#### The fan level is a dB index, not a percentage

`SetSwFanControlLevel(cpu, gpu, fan3)` sends a **128-byte** buffer to cmd `0x2E` but
only fills `b[0]`, `b[1]`, `b[2]`. The UI slider maps as:

```csharp
level = (int)((slider / 100.0) * SwFanControlTable.NumOfLevels + SwFanControlTable.MinRpm);
```

and `NumOfLevels = MaxRpm - MinRpm` (byte subtraction), with `MinDb = 33`.

`SwFanControlTable` parses the `0x2F` reply with **stride = `NumOfFans + 1`**, i.e. each
level tuple is **`[dB, fan1%, fan2%, (fan3%)]`** - byte 0 is a dB index, the rest are
percentages. `GetFanRpm(42)` is the "42 levels" reference.

**This corrects my §6.1 decode.** The three bytes per point are *not*
`(fan1%, fan2%, tempC)` - they are `(dB, fan1%, fan2%)` for a 2-fan board. The values
are still monotonic and still useful, but the first column is a dB level, not a
temperature.

#### Fan type nibble decode

`GetFanType` splits each of the first 4 bytes into two nibbles (`b[i] & 0x0F`, `b[i] >> 4`)
and takes 8 feature flags from `b[8]`. Our `0x2C = 0x21` → low nibble `1` = `Cpu`,
high nibble `2` = `Gpu`. Enum: `Unsupported=0, Cpu=1, Gpu=2, Exhaust=3, Pump=4,
Intake=5, Vrm=6, LightingBoard=100`.

#### Capability bits - independently confirms our SystemData decode

| Property | Expression | our byte 4 = `0x01` |
|---|---|---|
| `IsSwFanControlSupport` | `SystemDesignData[4] & 0x01` | **TRUE** |
| `IsExtremeModeSupport` | `SystemDesignData[4] & 0x02` | **FALSE** |
| `IsTwoBytePL4Support` | `SystemDesignData[4] & 0x10` | **FALSE** |

This reproduces our measured `SupportFlags = 0x01` exactly, from a completely
different source. Bit 4 being clear also means PL4 uses the **MSR** path, not cmd `0x37`.

#### Other gates worth replicating

- `IsBiosPerformanceModeSupport` requires `ShippingAdapterPowerRating >= 200 W`.
- `IsBigred24C1` returns true for SSID `8C9C` or `8C9D` - **our board is explicitly
  recognised**, but it only gates the **Fn+P hotkey**, not performance modes.
- Telemetry runs at **1 Hz** (`IntervalAlgoShort = 1000`) with a **30 s** heartbeat
  (`IntervalHeartbeat = 30000`), over a named pipe from a background service. A
  lightweight daemon can poll `0x21/0x23/0x2A/0x2D` directly at 1 Hz and skip the
  entire pipe/overlay stack.

#### Thermal thresholds (from `PlatformSettings` defaults)

`CpuOverheatThreshold=90`, `GpuOverheatThreshold=90`, `AmbientOverheatThreshold=70`,
`CpuTemperatureThreshold=90`, `CpuTemperatureThresholdLower=85`,
`GpsMaxTemperature=87`, `GpsMinTemperature=75`, `PchOverheatThreshold=108`,
`PchOverheatThreshold2=103`, `BatteryLowerBound=35`, `DtManualFanSliderLowerBound=20`.

#### Fan curve editor data model (for the UI)

`FanTable` is 12 `List<int>`s - 3 channels (CPU/GPU/IR) × 4 lists each:
`Temperature_List`, `Temperature_Low_List` (hysteresis floor), `Fan_Speed_List`
(raw), `Fan_Speed_List_UI` (display-mapped). Point *i* = `(temperature[i],
fan%[i])` with per-point `LowerBound[i]`/`UpperBound[i]` clamps.

Persistence keys are registry-based (`RegKeyCustomFanCurve`) with the typo
`IsEanble` preserved in the binary.

#### No GPU power table exists

There is **no TGP wattage slider** and **no per-GPU-model table** anywhere in these
assemblies. `CtgpMode` is a boolean toggle only. `0x21` reads
`{CTGP, PPAB, DState, GPS}` and `0x22` writes the same 4 bytes; `Gps` is a GPU peak
temperature target (87 °C). Our measured `00 01 02 57` decodes as CTGP=0, PPAB=1,
DState=2, GPS=0x57=87.

#### Undervolt ranges (Intel path, for reference)

`DefaultVoltageMaxValue = 0.995`, `MinValue = -0.995`, `CoreVoltageTick = 0.005`,
floor 0.5 V - an **offset in volts**, not mV. AMD Curve Optimizer is delegated to
`AMDRyzenSDK.dll` (managed, `Hp.Bridge.Client.SDKs.AmdRyzenSDK.AmdRyzenHelper`), with
`SetCurveOptimizerForAllCores`, `SetCurveOptimizerForEachCore`,
`SetPPTLimit`/`SetEDCLimit`/`SetTDCLimit`, `SetPBOScalar`. On this board the SMU
accepts those messages but they have no measurable effect (§4.7), so none of it is
worth exposing.

## 8. Recommended plan

The feature list is now bounded by hard evidence, not guesswork. HP's own
`DeviceList.json` says this board gets exactly: `SystemInfo`, `NetworkBooster`,
`FourZone`, `PerformanceControl`, `GraphicsSwitcher`, `PowerOption`, `OmenKey`. Of
those, `GraphicsSwitcher` is dead (BIOS err 5) and `NetworkBooster` is not worth
cloning. That leaves five features that genuinely work.

### Phase 1 - ship what is proven (low risk, high value)

1. **Fan curve reader.** `0x2F` → 42 points of `(fan1%, fan2%, tempC)`. Render it. This
   is the single most useful thing OGH does badly, and we can do it properly. Label it
   **read-only** - `0x32` is a no-op on this board, so do not offer an editor.
2. **Thermal mode switcher.** `0x1A` + payload `[0xFF, mode, 0, 0]`; confirm with
   `0x28[8]` (`0x1E` balanced / `0x23` performance). Modes worth exposing:
   `0x30` Balanced, `0x31` Performance, `0x50` Cool. Show the *actual* state byte, not
   an optimistic guess.
3. **Live telemetry.** CPU/GPU temps via `0x23` sensors 0–4; fan duty via `0x2D`; fan
   RPM via EC `0xB0–0xB3`; battery via `Win32_Battery`. No SMU PM table - it is static
   (§4.6).
4. **Keyboard RGB.** 3 zones at `0x1A + 3*i`, **RGB order**, read-modify-write the
   128-byte table on every set. Zone count comes from `colorTable[0]`, never from
   `0x2B`. Brightness via `0x05` (4-byte, level in `[0]`).
5. **BIOS settings editor.** All 23 enumerated settings via instance-path
   `SetBIOSSetting`, surfacing the calibrated return codes so a failure is explained
   (`1` = no such setting, `5` = value rejected, `6` = reboot required).
6. **Refresh rate switcher.** Pure Win32, no HP protocol: `EnumDisplaySettings` →
   `ChangeDisplaySettingsEx` with `CDS_TEST` first. Gated on Win11.

### Phase 2 - the real win: CPU power cap (5-25 W), now proven

7. **CPU power cap.** `0x29` with payload `{pl2, pl1, 0xFF, 0xFF}` writes `0x2A[2..4]`.
   The accepted range on this board is **5-25 W**; anything >= 26 W is rejected and the
   firmware resets the field to 25. Readback via `0x2A` is immediate and exact. This is
   a genuine, verified, working control - the first one found that actually moves a
   power limit.

   **It is a cap, not an unlock.** It cannot exceed the platform default. Expose it as
   a *thermal / noise / battery-life* slider, never a performance slider. Always
   restore on exit, and reapply at startup - the firmware resets to 25 W on its own.

   **Effect is proven, not assumed** (§3.3b): at 25 W the machine holds a steady
   3381-3393 MHz under 16-thread load; at 10 W it collapses to 1840-3058 MHz. The
   ranges do not overlap. This is a real control.

   Suggested UI: a 5-25 W slider with the live clock beside it, so the user sees the
   effect immediately. Default to 25 W (the firmware default) so the app is a no-op
   unless deliberately changed.

8. **Concurrent TDP / WithGpu.** `0x29` with `{0xFF, 0xFF, 0xFF, tdp}` writes `0x2A[7]`.
   Verified 7/7 across a 20-38-20 sweep with exact readback.

9. **SMU read-only diagnostics.** The mailbox works (§4.4). Expose SMU version
   (`MP1 0x02`) and PM table version/base as *diagnostics only*. Do **not** build a
   SMU power-limit UI: `MP1 0x14` is accepted and ignored (§4.7), and there is no
   readback.

10. **GPU mode - read only.** `GetGraphicsMode` (group 1, cmd 0x52, `& 0x7F`) works and
    returns `Discrete`. Show it. Do not offer a write - group 2 returns BIOS err 5.

### Phase 3 - only with a recovery path

9. **`_BTP` charge limit.** Requires a new namazso-signed PawnIO module exposing
   physical-memory access to the `0xFC7E0000` window, plus a hardware programmer for
   recovery. Low probability of success (§5.4). Do not start without explicit sign-off.

## 8.5 DEFERRED - does the 25 W ceiling depend on the power brick?

**Status: unanswered. Test instrument built, test not run.**

Every ceiling measurement in this document was taken with the factory 230 W
adapter **disconnected** — the machine was on USB-C PD throughout. That is a real
limitation of the evidence, not a detail:

- `0x28.DefaultPL4` reports **190 W**, far above the 25 W ceiling.
- OMEN Gaming Hub gates Performance mode on `ShippingAdapterPowerRating >= 200 W`
  (read from its own IL), so the platform clearly expects a ~200 W+ supply.
- The ceiling is invariant to load, thermal mode and idle/load state — measured.

So two readings remain possible:

1. **25 W is a hard platform policy** and the brick changes nothing.
2. **25 W is a reduced profile** the firmware applies while it sees a smaller
   supply, and `0x29` cannot override it because the ceiling sits upstream of the
   registers we can write.

`omenmon watch` exists to settle this. It logs `0x2A[0]`, PL1/PL2/PL4, `[7]`,
thermal status, live clock and AC state at 1 Hz. Procedure:

```
omenmon watch          # leave running
# attach the 230 W brick mid-capture
# if PL1/PL2/PL4 step above 25, reading 2 is correct
omenmon cap 40         # then confirm the ceiling itself moved
```

A 45 s capture on USB-C PD (recorded in `BRICK_TEST.txt`) shows the block pinned
at 25/25/25 with `[0]` drifting 55–61 and the clock at ~3970 MHz. That is the
baseline to compare against.

**Do not treat the 5–25 W window as final until this is run.** If reading 2 is
correct, the cap becomes a genuinely useful 5–190 W control instead.

## 9. Open questions

1. **What is `0x28[0]`?** It varies 60–62 at idle, never exceeds 65, and does not track
   load. Not watts. Possibly a thermal or utilisation scalar.
2. **Does `Legacy Support` do anything?** It accepts writes with rc=0 but never
   enumerates. Needs a reboot test.
3. **Is there a second BIOS settings namespace behind `SetSystemDefaults`?** Untested -
   the method is destructive and was not called.
4. **What value encoding does `Battery Care Function` want?** 27 encodings all rejected.
   A BIOS NVRAM dump would settle whether the platform flag is simply off.
5. **Why does `0x2B` report `0x04` while the colour table reports 3 zones?** Both are
   measured; OGH's enum disagrees with the firmware. Drive behaviour from the table.
